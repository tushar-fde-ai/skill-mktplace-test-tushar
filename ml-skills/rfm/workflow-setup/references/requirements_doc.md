# Phase 1: Requirements Gathering

Collect all information needed to configure the RFM workflow before touching any configuration files.

## Step 1: Locate the Customer's Confluence Folder

> **CRITICAL — Confluence requires unique page titles per space.** Every page you create in the CUST space MUST suffix the title with the customer name. Use the patterns below — never create a page titled simply `FDE Solutions`, `RFM Analysis`, or `RFM Requirements Gathering` because those titles already exist for other customers and the create call will fail with a 400 error.
>
> | Page type | Required title pattern |
> |---|---|
> | Customer root folder | `<Customer Name>` |
> | FDE/ML solutions sub-folder | `FDE Solutions - <Customer Name>` |
> | RFM solution sub-folder | `RFM Customer Segmentation - <Customer Name>` |
> | Requirements gathering page | `RFM Requirements Gathering - <Customer Name>` |
> | Configuration summary page | `RFM Configuration Summary - <Customer Name>` |
> | Architecture & schema page | `RFM Architecture & Output Schema - <Customer Name>` |
> | Runbook page | `RFM Runbook & Maintenance - <Customer Name>` |
>
> When **searching** for an existing folder by title, search for the un-suffixed name first (some legacy pages use the old un-suffixed pattern), then fall back to the suffixed version.

> **Do NOT include auto-generation disclaimers in published Confluence pages.** When you write the requirements gathering page (or any sibling page), do not add footer text like "Generated by fde-skills...", "This page was auto-generated...", or notes about the discovery queries you ran. The published page must read as if a human FDE author produced it. Discovery details belong in the chat session, not in the deliverable.

The customer documentation lives in the **Customers** Confluence space (CUST), organized by region:

```
Customers (CUST, space ID: 9797636)
├── US/ROWs    (page ID: 44728439)    → customer folders alphabetically
├── Japan      (page ID: 643963288)   → customer folders
└── Korea      (page ID: 1824266587)  → customer folders
```

Ask the user to identify the customer's Confluence folder using **one of two methods**:

### Method A: Search by Customer Name (Preferred)

Ask: **What is the customer name?**

Then search for their folder in the CUST space:

```
searchConfluenceUsingCql:
  cloudId: treasure-data.atlassian.net
  cql: space = "CUST" AND type = page AND title ~ "<customer_name>"
  limit: 10
```

From the results, identify the correct page by checking:
1. The page title matches or closely matches the customer name
2. The page's `parentId` is one of the three region pages (`44728439`, `643963288`, `1824266587`) — confirming it's a top-level customer folder, not a deeply nested subpage

If multiple matches are found, show them to the user and ask which one is correct.
If no matches are found, ask the user to provide a direct link (Method B).

### Method B: User Provides a Page URL or ID

Ask: **Can you paste a link to any page in the customer's Confluence folder?**

Extract the page ID from the URL. Confluence URLs look like:
- `https://treasure-data.atlassian.net/wiki/spaces/CUST/pages/<pageId>/Page+Title`
- `https://treasure-data.atlassian.net/wiki/x/<tinyId>` (tiny link — pass the `tinyId` to `getConfluencePage` as the `pageId`)

Once you have the page ID, read the page to get its `parentId`. If the page itself is the customer folder (i.e., its parent is a region page), use its ID. Otherwise, walk up the tree until you find the customer-level folder.

### Step 1b: Locate or Create the FDE Solutions Sub-Folder

Documentation pages should live under an **FDE Solutions** sub-folder within the customer folder — not directly under the customer root.

**Search for an existing sub-folder**:

Get the direct children of the customer folder and look for a match:

```
getConfluencePageDescendants:
  cloudId: treasure-data.atlassian.net
  pageId: <customer_folder_page_id>
  depth: 1
  limit: 50
```

Scan the results for a page whose title matches any of these patterns (case-insensitive):
- `FDE Solutions`
- `ML & Analytics Solutions`
- `ML & Analytics Projects`
- `ML Solutions`
- `ML Projects`
- `Analytics Solutions`
- `Analytics Projects`
- `FDE`

Also match titles that include the customer name as a suffix (e.g., `ML & Analytics Projects - SCI`).

If a match is found, use that page's ID.

**If no match is found**, create the sub-folder:

```
createConfluencePage:
  cloudId: treasure-data.atlassian.net
  spaceId: 9797636
  parentId: <customer_folder_page_id>
  title: "FDE Solutions - <Customer Name>"
  contentFormat: markdown
  body: "Landing page for Forward Deployed Engineering solutions deployed for <Customer Name>."
```

### Step 1c: Locate or Create the RFM Sub-Folder

Within the ML/FDE sub-folder, create (or find) a folder specific to the RFM project.

**Search for an existing RFM folder**:

Get the direct children of the ML/FDE sub-folder:

```
getConfluencePageDescendants:
  cloudId: treasure-data.atlassian.net
  pageId: <ml_fde_folder_page_id>
  depth: 1
  limit: 50
```

Scan the results for a page whose title matches any of these patterns (case-insensitive):
- `RFM`
- `RFM Analysis`
- `RFM Segmentation`
- `RFM Customer Segmentation`
- `Customer Segmentation`

If a match is found, use that page's ID.

**If no match is found**, create the sub-folder:

```
createConfluencePage:
  cloudId: treasure-data.atlassian.net
  spaceId: 9797636
  parentId: <ml_fde_folder_page_id>
  title: "RFM Customer Segmentation - <Customer Name>"
  contentFormat: markdown
  body: "RFM customer segmentation workflow documentation for <Customer Name>."
```

### Store the Folder IDs

Save both:
- **ML/FDE sub-folder page ID**
- **RFM sub-folder page ID** — you'll use this as the `parentId` when creating documentation pages in Phase 5

The final page hierarchy will be (every page suffixed with the customer name):
```
<Customer Name>
└── FDE Solutions - <Customer Name>                       (or legacy: ML & Analytics Projects - <Customer Name>)
    └── RFM Customer Segmentation - <Customer Name>       ← parentId for Phase 5
        ├── RFM Requirements Gathering - <Customer Name>
        ├── RFM Configuration Summary - <Customer Name>
        ├── RFM Architecture & Output Schema - <Customer Name>
        └── RFM Runbook & Maintenance - <Customer Name>
```

## Step 2: Check for Existing RFM Doc

Ask the user:

> Do you have an existing filled-out requirements gathering doc? If yes, paste the Confluence link.

If provided, read the page content using `getConfluencePage` and extract whatever configuration details are available (database, tables, columns, scoring preferences, etc.). Use the extracted values to pre-fill later steps, but still validate everything through auto-discovery.

## Step 3: Initial Questions

Collect answers to these questions before exploring any data. These determine the scope and complexity of the RFM configuration.

### 3a: Data Readiness

Ask: **Has the customer's data gone through ID Unification? Do they have a `gldn` database with enriched/unified tables?**

- If **yes**: The `join_key` will likely be `canonical_id` and tables will be in a `gldn_*` database
- If **no**: Ask — **Is there a unique identifier that can be used as the main `customer_id` across all tables?** (e.g., `cdp_profile_id`, `user_id`, `email`). This becomes `canonical_id` in the config.

### 3b: Behavioral Data Sources

Ask: **What customer interaction data is available in TD?**

Provide examples to prompt the user:
- Web activity / pageviews (from JS SDK)
- Email engagement (opens, clicks from SFMC/Marketo/Braze)
- Order / purchase history
- Sales rep interactions (calls, meetings from SFDC)
- App events / mobile activity
- Customer support interactions

Each source becomes an entry in `aggregate_metrics_tables`.

### 3c: Monetary Metric

Ask: **Which table and column represents the customer's monetary value (purchase amount)?**

Common patterns:

| Source | Column | Notes |
|--------|--------|-------|
| Orders table | `unit_price` | Line item price |
| Orders table | `total_amount` | Full order value |
| Orders table | `revenue` | Net revenue |
| Transactions table | `amount` | Transaction amount |

If no monetary data exists (e.g., non-commerce use case), RFM will use `order_amount: 0.0` for all tables and the M score will be uniform. Confirm this with the user.

### 3d: Time Filters & Business Rules

Ask: **Should we apply any time filters to the data?**

Options:
- **No filter** (default): Use all historical data — recommended for first-time setup
- **Lookback period**: e.g., last 180 days (`lookback_period: -180d`)
- **Fixed range**: e.g., 2023-01-01 to 2024-12-31

Ask: **Are there any business rules to apply?**

Examples:
- Only include orders where `order_status = 'COMPLETE'`
- Exclude bot traffic from pageviews
- Filter by specific region or market

### 3e: Scoring Configuration

Ask: **How many scoring bins should we use?** (Default: 10 for a 1-10 scale)

Options:
- `10` — standard decile scoring (most common)
- `5` — quintile scoring (simpler, easier to communicate)
- Custom — any integer

Ask: **Should we archive previous RFM results before each new run?** (Default: yes)

Ask: **Should we store historical scores for trending analysis?** (Default: no)

### 3f: Output Preferences

Ask: **Should we auto-build customer segments from the RFM scores?** (Default: no)

If yes, the workflow will create segment labels like "Champions", "Loyal Customers", "At-Risk", "Lost" based on R/F/M score combinations.

Ask: **Should we create a visualization dashboard?** (Default: yes)

## Step 4: Data Source Inventory

After initial questions, build a source table inventory. For each behavioral data source, collect:

| Field | Pageviews | Orders | Email | Sales/CRM | Other |
|-------|-----------|--------|-------|-----------|-------|
| **Table name** | `db.enriched_pageviews` | `db.enriched_orders` | `db.enriched_email_events` | `db.sales_rep_interactions` | `db.table_name` |
| **Description** | Web activity from JS SDK | Transaction history | Email engagement from ESP | Sales notes from SFDC | Custom source |
| **UNIXTIME column** | `time` | `time` | `time` | `time` | ? |
| **User ID column** | `canonical_id` | `canonical_id` | `canonical_id` | `canonical_id` | ? |
| **Order amount** | `0.0` | `unit_price` | `0.0` | `0.0` | ? |
| **Filters needed** | Bot exclusion | Status filter | Exclude 'sent' | NULL user filter | ? |
| **Contributes to** | R, F | R, F, M | R, F | R, F | ? |

**IMPORTANT**: For each table, you MUST identify:
1. The `UNIXTIME` column (often `time`, but may need conversion from datetime)
2. The `join_key` column (must be consistent across all tables)
3. Whether it has monetary data (`order_amount`)
4. What filters to apply (`custom_filter`)

Use `DESCRIBE` and `SELECT * LIMIT 10` via tdx-skills to fill in unknowns. See `table_configuration.md` for per-table-type discovery queries.
